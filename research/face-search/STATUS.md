2026-11-11 12:04–12:05 UTC 頃に実行環境との接続が切れ、その後の状態取得とファイル読出しが `No usable execution environment is available` で失敗した。完了済みの部分出力を含む作業ファイルは、現在回収できていない。削除されたと断定することも、残りの計測が完了したと断定することもできない。

このため、最初の実験は**未完了・元記録の回収待ち**として扱う。チャットの途中に表示された速度を、3 反復を検証済みの最終ベンチマークとして採用しない。

## 見つかった計時順序の問題

主実験では query ごとに方式の開始位置を循環させる。ただし、方式同士の隣接関係はほぼ同じであり、全件検索の直後に temporal が走る query が多い。

第 1 反復のログでは、temporal が結局全件検索へ戻った query でも、直前に全件検索を走らせた場合に速く見える傾向を観測した。キャッシュや allocator などの先行処理の影響と整合するが、それだけを原因だと断定した因果実験ではない。

**この循環実行を完全な順序均等化とは呼ばず、そこで得た倍率を単独エンジンの速度差として断定しない。** 元のプロトコル・コード・結果は保持し、別プロセスで 1 方式ずつ動かす追加診断を行う。

追加診断の順序は、元順で全件 → temporal → temporal → 全件、シャッフルで temporal → 全件。元順は各 2 反復、シャッフルは各 1 反復である。全 query を使い、warmup 後に履歴をリセットし、保存済み全件検索結果との照合はタイマーの外で行う。これは観測後に追加した診断であり、事前登録実験ではない。

## GitHub Actions での再実行

[再実行ワークフロー](../../.github/workflows/face-search-research.yml) を用意する。検索方式の主要 4 ファイルと元プロトコルは変更せず、まず全カタログと元動画の全フレームを準備する。

抽出し直した配列が元プロトコルの固定 hash と一致しなければ、速度計測を開始しない。データや許容値を自動で書き換えて検査を通す処理は入れない。

成功した場合も、新しいマシンでの 3 反復は独立した実験として扱う。中断したローカルの反復と合算しない。主実験と追加の独立診断も混ぜず、それぞれの環境、入力 hash、反復数、全設定の結果を残す。集計結果と診断記録は、そのワークフローの artifact から取得できる。

## 研究としての位置付け

この段階の成果は、Many Faces の照合部分を独立した研究対象にし、固定した採点式で検索速度と取りこぼしを比較できる実装を用意したことである。

既存 OSS を用いた検索構成と、上位候補を完全に保つことを狙う時間方向の方式の両方を比較する。既存方式が速い結果も残す。近い顔を 1 枚返す用途と、厳密な上位 64 候補が必要な用途では、優位性の条件が異なる。

1 本の合成済み動画、今回の NumPy 全件採点実装、サーバー CPU の結果だけから、未知の自然動画、スマートフォン、最適化された既存の厳密探索全般への優位性を主張しない。探索結果の再利用や距離上限による除外自体の新規性も主張しない。
