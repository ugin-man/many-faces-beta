# 通常動画パイプラインの改善

## 対象と判定基準

比較元は `00ef55256144c87e6dd642e1815a8f4071372c0e`。対象は通常の動画アップロードから解析、候補検索、系列選択、初期表示までである。Astra のカメラ用ベンチマークを通常動画の速度として扱わない。

候補数、解析 fps、入力解像度、検索の評価式、系列の目的関数を維持する。速度のためのフレーム間引き、画像縮小、候補の無言の欠落は行わない。数値を維持する計算の変更と、入力画素や推論結果が変わり得るエンジンの変更は、別々に検証する。

## 実装

| 工程 | 変更 | 維持する条件 |
| --- | --- | --- |
| 動画の読み出し | Mediabunny 1.65.2 と WebCodecs による連続デコード。未対応形式や途中失敗では未処理のサンプルから既存の動画要素経路へ復帰 | 全サンプルの順序、解像度、回転情報、明示的な中止。強制 WebCodecs 比較では復帰を成功扱いにしない |
| 顔解析 | 専用 Worker と、クリップ単位のエンジン寿命。初期化失敗時の main-thread / CPU 復帰を記録 | 既定は IMAGE / CPU。VIDEO の追跡と GPU は明示的な比較オプション |
| 検索データ | 原本の適格性判定を通した後、通常動画で使用しない shape / mesh を除いた派生カタログをビルド時生成 | 原本と画像は維持。版・形式・内部行が不正なら shard 全体を原本から読み直す |
| 検索 Worker | ジョブ ID を持つ再利用可能な Worker、版に結び付けた復号キャッシュ、上限付きの候補ウィンドウ | 前ジョブの完了処理を待って新ジョブを開始。品質除外条件は毎回適用。無操作 2 分で終了 |
| 投影比較 | ランカー内で不変な候補の記述量を再利用し、クエリは呼び出しごとに更新 | 計算の加算順序と数値を維持。外部の可変配列利用者にはキャッシュを強制しない |
| 候補選別 | 必要な先頭候補だけを exact Top-K で求める | 同点の順序を維持。全件が必要な場合、小集合、非有限値は従来の sort を使用 |
| 系列選択 | フレームごとに一定の表情量を事前計算し、同一終端の候補を生成中に集約 | 最良遷移の挿入順、重複 ID、反復・クールダウン、非有限値の扱いを比較元と一致 |
| 応答性 | 時間予算による協調的な譲り渡し、中止可能な系列選択、実処理の進捗 | 解析の 1 コマごとの描画待ちを不要にする。表示用の再生ループは描画時刻を使用 |
| 最初の表示 | 復号済み画像から保護済みの隣接画面と初期画面を作成 | 元映像の鮮度確認、不透明な顔の覆い、失敗時の保護画面を維持 |
| 診断 | 読み出し・推論・特徴量・待機・検索・系列選択・復帰理由・キャッシュを保存 | 別工程の時間を混ぜた速度主張を避け、実際に使った経路を確認可能にする |

キャッシュの上限は推定ペイロード 96 MiB / 30,000 件、ウィンドウは 2 個 / 40,000 参照である。JavaScript エンジンのオブジェクト管理費用を含む実際のヒープの上限を保証する値ではない。

Mediabunny は未改変の npm パッケージを使用し、配布物に `public/licenses/mediabunny.txt` のライセンスとソースの案内を含める。

## カタログ全件の生成結果

固定の原本 manifest SHA-256 は `fe90b250e37093bcf1ecb46b820cec98ece91e5bf2319681e0d3a3933767b03a`。

| 項目 | 実測値 |
| --- | ---: |
| shard 数 | 775 |
| 原本のレコード数 | 70,000 |
| 派生カタログに残ったレコード数 | 70,000 |
| 原本 shard JSON | 510,657,656 bytes |
| 派生 shard JSON | 329,637,326 bytes |
| 削減 | 181,020,330 bytes（約 35.4%） |

これは圧縮前の JSON ファイルの合計であり、動画 1 本が実際に受信する量、ネットワーク上の圧縮後サイズ、処理時間の削減率とは異なる。原本資産も配布するため、デプロイ全体の保存量は派生資産分だけ増える。新カタログがない既存環境では原本に戻る。通常のコード CI のように manifest だけがある checkout では生成を省略し、途中までしか揃っていない原本はエラーにする。

## 比較方法

`scripts/verify-video-pipeline.mjs` はリポジトリに以前からある公開サンプル `public/demo/many-faces-sample-30fps.mp4` を、全区間・既定 30 fps のまま使う。サンプルは約 35.4 秒、768 × 768、予定 1,061 コマである。既に顔が合成された公開動画なので、未加工の利用者動画やすべての撮影条件の代表とは主張しない。

比較は同じ runner の中で順に行う。

1. 固定した旧版、cold。
2. 改善版、旧読み出し / IMAGE / CPU / main-thread。検索に入る全数値と採用結果を厳密比較。
3. 改善版の既定経路、cold。入力差と採用差を別に記録。
4. 同じ画面で再処理、warm。キャッシュ効果を別に記録。
5. 受信を止めた状態で中止し、再処理が完了することを確認。

ブラウザ検証は、処理完了フラグだけでなく、画像ロード失敗、画素のある初期出力、再生・停止・コマ送り・seek を確認する。記録される実行 1 回の比率は、その入力と runner での観測値であり、端末全般の速度保証や統計的な性能評価ではない。

`scripts/verify-video-components.mjs` は読み出し画素、IMAGE / CPU の main-thread と Worker、VIDEO / GPU の結果を別に比較する。人工の回転・可変フレーム間隔の動画はデコーダの境界条件確認に限って使う。顔の検索品質をよく見せる入力には使わない。GPU を途中までに制限した場合は、そのコマ数を報告する。

GitHub Actions の `video-pipeline.yml` は PR でこれらを実行する。公開 artifact は集計、ハッシュ、実行条件、画面に限り、入力の全顔座標や全候補列は公開しない。ローカルの詳細出力は `work/` に置く。

## 比較オプション

| URL パラメータ | 値 | 既定 |
| --- | --- | --- |
| `mfDecoder` | `auto`, `webcodecs`, `video-element` | `auto` |
| `mfFaceMode` | `IMAGE`, `VIDEO` | `IMAGE` |
| `mfFaceDelegate` | `CPU`, `GPU` | `CPU` |
| `mfFaceExecution` | `auto`, `worker`, `main-thread` | `auto` |

VIDEO はフレーム間の追跡を使用するため、IMAGE と同じ顔座標や採用結果になるとは限らない。GPU も結果と初期化条件が異なり得る。既定を変更する際は、未検出、誤った向き、表情、採用写真、保護表示を別途比較する。

## 実装の検証と限界

固定した旧コードを独立した参照実装として、投影誤差、候補選別、系列選択の数値を照合する。同点、重複 ID、非有限値、可変クエリ、中止、待機処理の失敗を含む。実 Worker のテストでは warm 再利用、版変更、不正な compact データ、受信中止から次ジョブへの復帰を確認する。

ローカル確認ではビルドが成功し、Node の 349 テスト、Python の 238 テストが成功した。ESLint はエラー 0 件（変更外の既存警告 15 件）。TypeScript の `.ts` import 設定を実際の利用に合わせて修正した。リポジトリ全体の型検査には従来からの問題が残り、比較元の 44 エラーに対して変更後は 18 エラーである。全体の型検査が成功したとは扱わない。

作業環境では Chromium の socket 作成が禁止され、制限外の起動も自動承認審査で拒否された。管理済みブラウザもこの作業環境のローカルサーバーに到達できない。そのためローカルのビルド・単体/統合テストと、GitHub runner での実動画結果を区別する。ブラウザ結果がない段階で end-to-end の高速化率を記載しない。

Faiss 等への近似検索の置き換えはこの変更には含まない。現在の距離は複数の表情・投影条件と候補集合に依存し、単一の固定距離への置換が同じ採用結果を保つ根拠がないためである。全 sort、重複計算、不要データ、待機、再初期化を改善した後の実測を使って、近似検索の必要性と品質の許容範囲を判断する。
